# Auditoria técnica — 23/09/2026

## Resumo executivo

O `mcp-fiscal-brasil` já é uma base relevante para automação fiscal por agentes, mas o fork `lloupp/mcp-fiscal-brasil` estava 56 commits atrás do upstream canônico. Esta auditoria sincroniza a base 0.5.1 e aplica um primeiro lote de hardening orientado por confiabilidade.

Arquitetura-alvo:

> **mcp-fiscal-brasil = infraestrutura aberta, stateless, auditável e composável**  
> **APURA = produto comercial multi-tenant, com teses, workflows, credenciais, evidências e revisão humana**

## Inventário

- **MCP:** 47 tools registradas.
- **REST:** 16 rotas; subconjunto seguro do core, não paridade completa.
- **CLI:** 10 comandos; foco em consulta, triagem e capability discovery.
- **SDK Python:** módulos públicos para integração server-side.
- **Distribuição:** PyPI + `server.json` para MCP Registry + wrapper Node preview.
- **CI:** Python 3.10–3.13, Ruff, Mypy e Pytest; CodeQL e auditoria OSV.

### Cobertura MCP por domínio

| Domínio | Estado | Observação |
|---|---|---|
| CNPJ/CPF | forte | CNPJ com fallback e suporte alfanumérico; CPF é validação matemática, não consulta cadastral |
| Simples/MEI | operacional | usa campos reais de `/cnpj/v1`; BrasilAPI é agregador, não autoridade |
| NF-e/NFC-e | forte | chave, XML, assinatura, DANFE, status SEFAZ, distribuição e manifestação |
| NFS-e | intermediário | ADN nacional com A1 + fallback municipal; falta validação RTC completa |
| SPED | intermediário/forte | EFD ICMS/IPI, EFD-Contribuições, ECD e ECF; falta suite de layouts/versionamento |
| eSocial | básico | catálogo + validação estrutural, sem validação XSD oficial completa |
| IBS/CBS/Reforma | intermediário | simulador 2026–2033; falta validador documental RTC |
| Tabelas fiscais | útil, condicionada | NCM/CFOP/CST/CSOSN/CEST/ICMS; precisa vigência e proveniência por linha |
| Importação | MVP | estimativas e NCM; faltam TEC integrada, DUIMP e regimes especiais |
| Certidões | orientação | federal/FGTS retornam caminhos/URLs; não atestam regularidade automaticamente |
| BCB/IBGE/CEP | forte para apoio | fontes públicas/oficiais conforme o domínio |

## Achados críticos corrigidos neste PR

1. **Fork defasado:** branch passou a usar o upstream atual como base.
2. **Simples/MEI:** removida dependência de `/simples/v1`, endpoint inexistente na BrasilAPI atual; os campos são lidos do cadastro CNPJ.
3. **NF-e pública:** removida automação de consulta protegida por CAPTCHA; XML oficial fica em `NFeDistribuicaoDFe`/A1 ou provider autorizado opt-in.
4. **Proveniência:** nova tool `listar_fontes_fiscais` informa classe, confiabilidade e limitações da fonte.
5. **Capability discovery:** nova tool `listar_capacidades_fiscais` informa recursos habilitados sem revelar secrets.
6. **Filesystem:** tools MCP por caminho só leem `MCP_FISCAL_FILE_BASE_DIR`.
7. **A1:** senha/caminho do certificado saíram do schema das tools de distribuição/manifestação; vêm do secret/config do processo.
8. **Supply chain:** GitPython 3.1.59 atualizado para 3.1.60 após três vulnerabilidades altas detectadas pelo OSV.
9. **Reforma 2027–2028:** simulador corrigido para representar CBS com redução de 0,1 p.p. e IBS de 0,1 p.p.; 2026 registra nominalmente CBS 0,9% + IBS 0,1% e compensação no modelo.

## Fontes e confiança

Hierarquia recomendada para agentes:

1. autoridade oficial autenticada / especificação oficial;
2. cálculo determinístico offline com tabela versionada;
3. agregador público com origem explícita;
4. provider privado opt-in;
5. heurística/estimativa, sempre rotulada.

`BrasilAPI` e `ReceitaWS` não devem ser descritas como Receita Federal. Ausência de resposta não deve virar automaticamente um fato fiscal negativo.

## Gaps prioritários

### P0 — confiabilidade

- versionar tabelas fiscais com fonte, versão, `valid_from` e `valid_to`;
- adicionar limites de tamanho/streaming para XML e SPED em todas as interfaces;
- remover/mascarar identificadores completos em logs onde não forem necessários;
- transformar scores de fornecedor e comparador de regimes em apoio analítico, nunca decisão automática;
- completar validação XSD/versionada de NFS-e/eSocial;
- health/capabilities de fontes externas sem expor credenciais.

### P1 — ferramentas fiscais que resolvem trabalho real

- validador RTC de NF-e/NFC-e/NFS-e: grupos IBS/CBS, CST, classificação tributária e vigência;
- CT-e, CT-e OS e MDF-e: parse, chave, eventos e distribuição;
- EFD-Reinf e integração conceitual com DCTFWeb/MIT;
- conciliação `XML de entrada ↔ SPED ↔ razão/ERP`;
- classificação fiscal de item com NCM/CEST/CFOP/CST/CSOSN e vigência;
- DeRE e documentos do cronograma RTC;
- DUIMP/tributos de importação com adapters oficiais/versionados;
- GNRE via adapter autenticado quando houver integração adequada.

### P2 — ecossistema de desenvolvedores

- JSON Schemas/versionamento semântico das tools;
- conformance suite para providers/adapters;
- examples para clientes MCP genéricos e frameworks de agentes;
- golden fixtures anonimizadas;
- protocolo de adapters ERP;
- telemetria opt-in sem conteúdo fiscal.

## Workflows compostos para agentes

### Recebimento fiscal

`documento → parse → assinatura/chave → emitente → classificação → regras RTC → conciliação → achados → revisão`

### Fechamento

`SPED → layout/período → consistência → XML/ERP → divergências → evidências → revisão`

### Cadastro/fornecedor

`CNPJ → situação → regime → certidões autorizadas → evidências → fila de revisão`

Score heurístico não deve aprovar ou recusar fornecedor sozinho.

### Reforma tributária

`item/serviço → classificação → IBS/CBS vigente → validação DFe → impacto por período → evidências`

## Integrações ERP e escritórios

Definir um adapter mínimo no open source:

- `list_companies()`;
- `list_documents(company, period)`;
- `get_document(id)`;
- `get_ledger_period(company, period)`;
- cursor de sincronização/idempotência;
- envelope de proveniência.

Credenciais, OAuth, refresh, filas, webhooks e SLA de Omie, Conta Azul, Bling/Olist, TOTVS, Sankhya, Domínio, Alterdata, Senior e SAP pertencem ao APURA ou a plugins separados.

## Integração APURA

O APURA hoje duplica parsers e consulta CNPJ no próprio código. A migração deve ocorrer por estrangulamento:

1. fixar uma versão do `mcp-fiscal-brasil` no APURA;
2. substituir primeiro validadores/parsers duplicados por SDK Python;
3. preservar outputs do APURA via adapters compatíveis;
4. persistir um `evidence envelope` com versão da tool, fonte, timestamp, hashes, limitações e revisão;
5. manter `auth`, tenant, `teses.py`, monitor jurídico, e-CAC, geração de documentos e billing no APURA;
6. usar MCP para composição dinâmica por agentes, nunca como fronteira de autorização multi-tenant.

## Critério de release

Release somente após CI, CodeQL e supply-chain verdes, metadata de versão consistente e confirmação de ownership/publicação do pacote PyPI/MCP Registry. O fork não deve publicar sobre o namespace canônico por acidente.
